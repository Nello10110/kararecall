# Socle P0 : mise en place et qualification

État du 5 novembre 2026, pour environ vingt vidéos par mois. Le socle technique ci-dessous est implémenté. La qualification avec vos clés, vos services et votre NAS reste nécessaire ; aucun appel IA facturé n’a été lancé pendant ces vérifications.

## Fonctionnement livré

- Une publication se prépare dans `data/generations/…`. Les médias et les preuves immuables peuvent partager leurs fichiers ; les extractions modifiables sont copiées. Le catalogue et les Markdown sont reconstruits et validés avant le remplacement atomique de `data/current.json`. Un lecteur conserve la même génération pendant sa requête. Un échec avant publication laisse la génération précédente disponible.
- Les preuves reçoivent un identifiant calculé à partir de leur contenu et provenance, avec modèle/configuration et empreinte média pour les extractions. Les captures citées sont conservées par empreinte. La première publication migre les anciennes références avant de modifier les sources ; les anciennes preuves restent accessibles, signalées comme telles dans l’interface et le contexte exporté.
- Le worker exécute audio et vision indépendamment. Une panne audio n’empêche pas de publier un OCR réussi. Une vidéo sans piste audio ne provoque aucun appel ASR et prend l’état « non applicable ». La synthèse attend les étapes configurées en échec plutôt que de présenter silencieusement une fiche comme complète.
- Les caches incluent fournisseur, modèle demandé, paramètres et version du traitement. Les captures reconnues sont mémorisées individuellement dans `data/work/…` ; une reprise ne les renvoie pas toutes. Le cache de travail est séparé des générations publiées. Une interruption après un appel distant dont le résultat n’a pas pu être enregistré peut néanmoins nécessiter un nouvel appel : aucune garantie de facturation exactement une fois n’est annoncée.
- Trois tentatives automatiques par source/configuration par défaut. Ensuite, une reprise volontaire est nécessaire. Les pauses de quota/budget ne consomment pas ces tentatives et reprennent lorsque l’allocation redevient disponible. Les sources en attente et les étapes en erreur sont visibles. Une absence prolongée d’état du worker est signalée par le web.
- Le budget d’entrée de synthèse est réparti entre modalités et portions disponibles ; la fiche conserve une indication de couverture. Les sorties texte et vision sont limitées en tokens ; le paramètre de limite et le raisonnement sont configurables selon le serveur.

La recherche reste lexicale. Le corpus reste en lecture seule dans le web ; le bouton d’import ajoute une demande locale à la file du worker. La recherche internet automatique, MCP, l’éditeur de fiches et les embeddings ne font pas partie de ce lot.

## Profil DeepSeek et import initial

Le profil recommandé est désormais `python3 scripts/setup_env.py --profile deepseek`, avec DeepSeek Flash pour texte et captures, audio non configuré et tous les favoris inclus. Le bouton **Importer tout l’historique** importe le catalogue sans IA. Voir [IMPORT-ET-DEEPSEEK.md](IMPORT-ET-DEEPSEEK.md) pour la procédure actuelle. La section suivante conserve l’alternative Groq/OpenAI ; ne pas mélanger leurs clés ou paramètres.

## Profil API alternatif prêt à renseigner

```sh
python3 scripts/setup_env.py --profile api
```

Le script crée `.env` avec un mot de passe web aléatoire et les adresses/modèles suivants : Groq `whisper-large-v3-turbo` pour l’audio, OpenAI `gpt-6-luna` pour les captures et les fiches. Ce sont des paramètres modifiables, pas des comptes fournis ni une validation de qualité. Les tarifs du profil reprennent l’étude datée et doivent être vérifiés avant activation.

Le script refuse de remplacer un `.env` existant et n’en affiche pas les secrets. `--profile empty` conserve les moteurs non renseignés. Dans tous les cas, synchronisation et synthèse restent désactivées jusqu’à modification volontaire du fichier. Le worker est absent du lancement tant que le profil Compose `automation` n’est pas activé.

À renseigner dans `.env`, sans envoyer les clés dans le chat :

| Paramètre | Valeur attendue |
|---|---|
| `KARAKEEP_BASE_URL` | Adresse de votre serveur Karakeep |
| `KARAKEEP_API_KEY` | Clé permettant les lectures |
| `LLM_API_KEY` | Clé OpenAI du profil proposé ; la vision hérite de cette clé si sa clé est vide |
| `ASR_API_KEY` | Clé Groq du profil proposé |
| `KARAKEEP_URL_FILTER` | Vide par défaut pour tous les favoris |
| `KARAKEEP_TAG_FILTER` | Noms de tags facultatifs séparés par des virgules ; au moins l’un doit correspondre |

Le filtrage par liste Karakeep n’est pas implémenté. Les filtres URL et tags se combinent. Pour une collecte de textes seuls, garder `LLM_ENABLED=false` et vider `ASR_MODEL` et `VISION_MODEL` avant d’activer la synchronisation ; un modèle audio/vision renseigné active son étape lorsque la collecte fonctionne.

## Contrôler puis lancer

Après avoir renseigné la configuration, garder la boucle automatique arrêtée pour le premier passage :

```sh
# Démarrer d’abord la consultation.
docker compose up -d --build web
# Vérification d’accès et de modèles uniquement, aucune inférence.
docker compose --profile automation run --rm --build worker python worker.py check
# Activer SYNC_ENABLED=true et LLM_ENABLED=true dans .env pour le profil complet.
# Réduire WORKER_BATCH_SIZE=1 pour le premier essai sur le périmètre choisi.
docker compose --profile automation run --rm worker python worker.py once
# Vérifier l’intégrité du corpus publié, sans appel réseau.
docker compose exec -T web python verify_storage.py
```

Contrôler la fiche et ses preuves dans le web. La commande `check` ne prouve pas la compatibilité d’inférence ; seul le passage réel la vérifie. Puis régler `COMPOSE_PROFILES=automation` dans `.env` et lancer `docker compose up -d --build` pour la boucle. Modifier `.env` puis recréer les services applique les nouveaux paramètres. Aucun service sur le NAS n’a été modifié par ce travail.

Pour relancer volontairement une source, arrêter la boucle puis utiliser son identifiant Karakeep :

```sh
docker compose --profile automation stop worker
docker compose --profile automation run --rm worker python worker.py retry --source ID_FAVORI --stage asr
docker compose up -d
```

`--stage` accepte `asr`, `vision`, `llm` ou `all`. Il invalide explicitement le cache de l’étape visée pour cette source ; les autres étapes configurées sont contrôlées/reprises si nécessaire. La source doit appartenir au périmètre de collecte courant. Le budget et les quotas restent appliqués aux reprises volontaires.

## Budget et journal d’usage

Valeurs par défaut : 2 USD/mois, 50 appels par jour, 400 par mois, réserve de 0,05 USD par appel, trois tentatives automatiques. Les périodes du journal sont en UTC. Cela constitue une limite comptable de l’application, pas une garantie du montant facturé par un fournisseur.

Avant chaque requête, une réservation durable est inscrite dans `data/usage.sqlite`. Si le quota ou le budget ne permet pas cette réservation, aucune requête n’est envoyée. Lorsqu’un service rapporte les tokens et que les tarifs sont renseignés, la réserve est remplacée par un coût calculé. L’audio est estimé à partir de la durée et du tarif horaire, avec le minimum de dix secondes du profil Groq. Les erreurs et les appels sans usage/tarif connu gardent toute leur réserve, y compris après redémarrage. Les clés, prompts et réponses ne sont pas enregistrés dans ce journal.

Le compteur est accessible dans Traitements et via :

```sh
docker compose --profile automation run --rm worker python worker.py usage
```

Paramètres principaux : `AI_MONTHLY_BUDGET_USD`, `AI_CALL_RESERVE_USD`, `AI_MAX_CALLS_PER_DAY`, `AI_MAX_CALLS_PER_MONTH`, `WORKER_MAX_ATTEMPTS`, `LLM_MAX_OUTPUT_TOKENS`, `VISION_MAX_OUTPUT_TOKENS`. Tarifs : `LLM_*_USD_PER_MILLION`, `VISION_*_USD_PER_MILLION`, `ASR_USD_PER_HOUR`. Une valeur de tarif nulle signifie inconnue, sans annoncer un coût gratuit.

Le profil générique peut donc s’arrêter tôt si le fournisseur ne rapporte pas d’usage : c’est volontairement conservateur. Si un coût calculé dépasse la réserve par appel, les nouveaux appels du mois sont suspendus ; vérifier les tarifs et la réserve, puis choisir explicitement un budget révisé ou attendre la prochaine période. Vérifier aussi les limites de dépenses du fournisseur : une estimation erronée ou une facturation différente ne peut pas être annulée par le client.

## Stockage et sauvegarde

Une fois `data/current.json` créé, les données courantes sont sous la génération qu’il désigne. Les chemins `data/…` et `vault/…` du catalogue sont relatifs à celle-ci. Ne pas modifier directement une génération publiée ni éditer les anciens JSON à la racine en pensant modifier la bibliothèque courante. Pour une modification administrative : arrêter le worker, créer un brouillon avec `publication.generation`, modifier son `data/entities.json`, puis appeler sa fonction de publication. L’éditeur web est un travail ultérieur.

Le coffre privé historique reste utilisable avant migration. La recherche CLI suit automatiquement la publication courante ; le pipeline macOS historique refuse de modifier une bibliothèque déjà publiée. `kararecall.py build` reconstruit une nouvelle génération lorsqu’une publication existe.

Sauvegarder le volume complet (`data/` et `vault/`) et le `.env` de l’hôte séparément. Les caches de travail peuvent être recréés, mais perdre leur état peut provoquer de nouveaux appels. Les anciennes générations sont conservées, sans suppression automatique ; elles occupent de l’espace et restent à intégrer à la politique de rétention.

```sh
docker compose stop
# Archive binaire, sans inclure le fichier .env de l’hôte.
docker compose run --rm --no-deps -T web tar -C /workspace -czf - data vault > kararecall-backup.tar.gz
# Sur un volume neuf préparé pour la restauration :
docker compose run --rm --no-deps -T web tar -C /workspace -xzf - < kararecall-backup.tar.gz
docker compose run --rm --no-deps -T web python verify_storage.py
docker compose up -d
```

Ne pas restaurer par-dessus une bibliothèque active. Le [guide homelab](HOMELAB.md) décrit volume, réseau, droits et mises à jour. `verify_storage.py` contrôle références, empreintes et présence des captures sans modifier les données ; il ne juge pas la justesse des synthèses.

## Vérifications réalisées et restantes

Réalisé localement : tests de génération atomique et d’échec de publication, migration des références, images immuables, caches et reprise partielle des captures, vidéo sans piste audio, séparation des étapes, limites de sortie, budget/quota avant réseau, historique de consommation après réouverture du journal, refus des chemins non autorisés, authentification et requêtes vidéo partielles.

Sous OrbStack/Linux ARM64 : démarrage vide, corpus synthétique versionné, authentification, recherche et exports, sauvegarde puis restauration sur un second volume neuf avec vérification d’intégrité. Les seules ressources de test créées par ces contrôles sont ensuite supprimées. Les tests média utilisent une vidéo synthétique et des API locales simulées, sans fournisseur payant.

Une migration sur une copie temporaire du corpus privé du POC conserve 33 sources, cinq fiches et la recherche ; les fichiers originaux n’ont pas été modifiés. Dans le navigateur, la citation d’une ancienne transcription affiche sa preuve conservée et permet de lire une vidéo synthétique H.264 à l’instant cité.

Restent à réaliser avec l’utilisateur : renseigner les clés, qualifier les contrats et résultats réels sur vingt sources variées, déployer sur le NAS et y tester restauration/mise à jour et ressources. La recherche web systématique reste dans P1 ; le budget de l’étude la prévoit, mais aucun fournisseur de recherche n’est appelé par cette version.
